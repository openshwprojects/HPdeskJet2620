What this adds to the analysis:
  fm.carriage_home uses the same generic handler as fm.version_query (0xa00e084a). 57 fm.*
  descriptors share it. The descriptor's context word is the callback that the fm task should
  run. version_query: 0xa00e0cb1 only formats three numbers through 0xa00e0826.
  carriage_home: 0xa00e2455 calls 0xa00dd4d6(0x21) and prints nothing.
  Both hung, so the earlier guess (fm-task output deadlocking with the waiting shell) does not
  explain this hang. The likelier explanation is that the fm task is not servicing message 0x49
  at all in the printer's normal state, but that is unproven. Until it is, treat every
  generic-handler fm.* command as one that hangs the shell.

Built-in "hello world" job test: temp.job and temp.async (user-requested)

The firmware contains two "hello world" strings at 0xa061e300 / 0xa061e30c, referenced only by
temp.job (handler 0xa042d09e) and temp.async (handler 0xa042d11c). Both submit a fixed built-in
test job to the job scheduler (the TEMP_AGENCY task that "smjob show" lists as RUNNING) and print
the result. They are ordinary registered UDW commands, not fm.*, and both returned the prompt.

  udws "temp.job;"      submit_job(mem_size = 0, tid = 68988) : OK
  Source: physical-83-temp-job/0001-udws_temp_job.bin

  udws "temp.async;"    async_call(parm = hello world) : OK
  Source: physical-84-temp-async/0001-udws_temp_async.bin

  tid 68988 = 0x10d7c is the default job id compiled into temp.job's handler. temp.async passes
  the literal "hello world" string as the job parameter, which is why the reply echoes it.
  The job body is fixed in firmware; this is a built-in diagnostic, not a path to run supplied
  code. It is, however, a non-hanging "schedule a job, get OK" path, unlike the fm.* family.
  Static call-graph analysis flagged a path from both handlers to the same blocking primitive
  (0xa02f5fa2) used by the fm hangs, but in practice both completed and returned the prompt:
  they wait on the TEMP_AGENCY task, which services the job, not on the fm task.

Lua interpreter attempt (user-authorized, restart accepted)

  fm.luau   (handler 0xa00e0f58 -> worker 0xa00e0f24): RETURNED, no hang.
    udws "fm.luau;"  ->  99999;udws() returns 0 (0x0)
    Source: physical-85-fm-luau/ (probe sent the command, then would have flushed input if it
    had blocked; it did not block).
    This handler does NOT run Lua. It reads characters from input stream handle -1 via the
    buffered getc at 0xa02c2a3a into a 256-byte stack buffer until EOF(-1) or full, null-
    terminates, then prints the fixed string "%05d%c" with 99999 (0x1869f) and ';' through the
    UART writer at 0xa00e0826 (snprintf 0xa0016ed0 + writer 0xa02c2a7a). With no buffered input
    the first getc returned -1 immediately, so it printed "99999;" and returned. Not an
    interpreter; the "luau" name is misleading.

  fm.lua   (generic handler 0xa00e084a): HUNG the shell.
    udws "fm.lua;"  ->  echo only (16 bytes), no prompt; empty CRLF afterward got nothing (86b).
    Power cycle required. Same post-to-fm-task-and-wait-forever pattern as fm.version_query and
    fm.carriage_home.
    fm.lua_download, fm.lua_restart and fm.lua_gc share handler 0xa00e084b, so they hang
    identically; they were not fired individually.

Conclusion: no usable "run supplied code" path over UART. The real Lua entry (fm.lua) hangs
because the fm task does not service these messages in this firmware state; fm.luau does not
execute Lua. The firmware's working "run something and get a result" path is the built-in
hello-world job test temp.job / temp.async (see the section above).

Native ludw re-confirmed after restart (session 88)

ludw is a native shell function (not a UDW registry name) that runs UDW expressions through the
same interpreter and output callbacks as udws. First exercised in session 20; re-confirmed here.

  ludw "shm.msecs;"                 -> msecs = 67762 ; ludw() returns 0   (uptime ~68s: fresh boot)
  udw_tags on                       -> udw_tags() returns 0
  ludw "bio.rev_str; shm.msecs;"    -> <udw>TJP1FN1809AR;</udw><udw>msecs = 68696</udw><udw>;</udw>
  udw_tags off                      -> udw_tags() returns 0
  Source: physical-88-ludw/

udw_tags on/off toggles wrapping each UDW expression's output in <udw>...</udw> tags.
ludw uses the same interpreter as udws, so it is NOT a workaround for the fm.* hang
(ludw "fm.version_query;" would hang identically) and does not fix the bulk-output truncation.

Note: the fm.luau probe (session 85) logged its reply to physical-85-fm-luau/transcript.txt but
used manual send/receive rather than the capture executor, so it has no per-command JSON record
and the index marks fm.luau not-invoked. The raw reply "99999;udws() returns 0" is in that
transcript and in round8-results.txt above.
