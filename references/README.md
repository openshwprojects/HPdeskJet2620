# Physical DeskJet 2620 UART reference

These captures were made directly from the user's printer on COM16 on 2026-10-29, at 115200 baud, 8 data bits, no parity, one stop bit, and no flow control. DTR and RTS were held false. The printer reported firmware `TJP1FN1809AR`, base firmware `TJP1FN1702CR`, board ID `0x68a4`, and SKU `2620`.

## Where the per-command files went (2026-11-05)

Each command used to be stored as four files in its session folder: a `.json`
record, the reply (`.bin` and `.txt`) and the bytes sent (`.tx.bin`). These
13,892 files were removed from the tree because nothing in them was unique:

- every per-command record is one line of [per_command_records.jsonl](per_command_records.jsonl),
  with its original `path` (e.g. `physical-09-registry/0001-udws_udw_iter_reset.json`);
- every text reply is contained in full in [all_uart_output.txt](all_uart_output.txt)
  (checked line by line for all of them); replies that are not plain text stay in
  their folders (NVM header and RAM-mirror dumps, the raw `rx.bin` logs of sessions
  01, 02 and 81-89), as do `session.json`, `runtime_inventory.json` and the `.jsonl` session logs;
- the bytes sent are the `command` field of each record.

Paths to individual per-command files in [command_index.md](command_index.md),
`command_results.json` and `coverage.json` are now identifiers. The original files are in
git history: `git checkout ae204c6 -- references/<path>` restores one (or a whole session
folder), which is also needed before re-running the `assess_*.py` scripts that re-check reply hashes.

The complete registry is a list of available commands. It is not a claim that every operation or argument combination has been exercised. A transmission can contain several UDW expressions, so UART-line counts and command-expression counts differ. A usage response or empty-argument guard tests that path only. A compiled-out handler returning immediately does not exercise the operation suggested by its name. The index preserves these distinctions. Commands without a test are not assigned invented output.

Review notes apply to the exact named path and batch described in their source. An earlier operational-path hold can coexist with a later guard/stub test or a separately reviewed invocation. Missing review evidence is not a finding that a command is dangerous. [status-prerequisite-results.json](status-prerequisite-results.json) records the live bounds that admitted three further getters and held five scan-string getters with zero record-count/size metadata. Session 27's `jm_urf.get_perf_timers` invocation printed four zero timing counters and then cleared those four volatile RAM counters; this read-and-clear side effect is preserved explicitly.

Native shell functions and variables have a separate registration mechanism. Static candidates, attempted function names, functions that printed their own return marker, and variables that returned a value are distinguished in the records and summary. UDW wrapper calls containing command strings count as UDW batches; the native wrappers' empty-argument tests count as native function calls. A returned prompt alone does not establish that a name was recognized.

## Capture format

Each `physical-*` directory contains a session description, timestamped `wire.jsonl` with host TX requests and exact received bytes, an aggregate `rx.bin`, and a readable transcript. Completed command attempts have individual `.tx.bin`, `.bin`, `.txt`, and `.json` files. TX events are logged before sending; a command's `.tx.bin` is saved after the host write completes. Response metadata includes elapsed time, prompt detection, and SHA-256. [capture_integrity.json](capture_integrity.json) checks the received-byte event stream against each aggregate binary capture. The index builder also checks event lengths and offsets, per-command lengths and hashes, and command TX files against the logged bytes.

Byte integrity establishes that the saved files agree; it cannot establish that the firmware emitted all intended data. Typed storage capture validation is recorded separately in `validation`. A `response-validation-failed` result can have a returned prompt and intact capture hashes while still failing expected field, type, or count checks. Full-NVM structural validation is recorded separately as `payload_validation`. Known reset-table losses appear in `data_quality`, with missing DSIDs, source hashes, and recovery evidence; their individual results are labeled `output-returned-incomplete` even though the prompt returned. Later `post_capture_validation` assessments are tied to the exact source-response hash and never replace the original capture status, validation, or failure outcome. Error, usage, assertion, silent-unregistered, malformed-bulk, and timeout outcomes retain their original responses.

Session 19 line 26 stopped because the initial host validator incorrectly limited a wire value to signed 32-bit range. The printer's `4294967295` is a valid unsigned 32-bit value. The corrected parser revalidated the original responses, and session 19b resumed acquisition. The historical `response-validation-failed` label remains alongside the successful later assessment; this was a decoder error, separate from the actual missing characters in full-NVM sessions 12/13 and reset-table sessions 16/18.

`capture_uart.py` sends only the commands supplied in an explicit JSON batch. It stops if the shell prompt does not return, or if optional `--validate-storage` checks reject a response. Current transmission uses CRLF and paced characters. The receive loop coalesces bytes and requests a larger Windows receive buffer for sustained output. Earlier sessions retain the settings actually used at the time.

`enumerate_uart.py` resets only the command-enumeration cursor and repeatedly requests the next names. Listed commands are not executed during enumeration. `listen_uart.py` records without transmitting anything. `build_reference_index.py` rebuilds the combined transcript, plain command-name list, and coverage from existing captures. Active sessions are listed in the summary but their responses are indexed only after the session closes or stops, avoiding inconsistent reads while capture files are being written.

## Observed interruptions and limitations

- `rev.get_aasic` produced assertion `0xc4eb99f7` in `hw_micci2.c`, line 1733, during the first information batch. The user subsequently reported unplugging the printer and restarting it. The timing is uncertain, so this is not evidence that the command always fails. The captured fault was a read from the carriage companion: controller `0xBD300C00`, bus 1, device 4, register `0x7D`. See [query_review.json](query_review.json) for the instruction evidence and the original session for the full stack dump.
- `fm.version_query` (session 80) and `fm.carriage_home` (session 82) each blocked the UDW shell indefinitely: echo only, then no response even to an empty line. Each needed a power cycle. The shared handler waits forever on a reply from the `fm` task; see [round8-results.txt](round8-results.txt).
- Some CR-only commands stalled after the restart with the command echo but no completed response. CRLF restored reliable command completion. The interrupted attempts and subsequent recovery output remain in the capture directories.
- **Both** sustained `nvm2.nvm_read_all` attempts, sessions 12 and 13, have interior missing characters and end at `;ud` without a prompt. Their fixed-width data bodies are short by 17,658 and 17,673 bytes; tokens such as `25255` cannot represent byte values. Neither is a validated 65,536-byte NVM image. [bulk_output_analysis.json](bulk_output_analysis.json) records hashes, malformed field counts, timing, and output-path evidence. The larger host receive buffer did not resolve the second capture. The exact loss mechanism remains unproven; switching to `ludw` uses the same interpreter and output callbacks.
- Empty output can be a real result. `udw.cmds` has a firmware gate; several registered handlers are compiled as no-ops. Conversely, `udw.mem_read` is absent from the complete physical registry: its two session-17 attempts silently returned wrapper status zero without a payload. They are marked `runtime_registered: false` and `silent-unregistered-command`, and provide no memory-read result. The native `help` and `CIRBUF_debug` attempts explicitly returned “I don't understand.” A returned shell prompt or `udws() returns 0` does not prove meaningful data or successful dispatch.

## Offline supporting analysis

[static_inventory.json](static_inventory.json) and [inventory_extractor.py](inventory_extractor.py) describe descriptors and argument evidence from the reconstructed 2018 image. This is separate from the physical registry and responses. The extractor verifies all 21 reconstructed image ranges and records its source hashes. Static candidates can be absent from the live registry.

The `*_query_review.json` files and [help_review.json](help_review.json) record why particular invocations were selected. [check_empty_argument_paths.py](check_empty_argument_paths.py) checks guarded empty-argument paths offline; its modeled parser results are analysis evidence, never physical test output. [native_guard_review.json](native_guard_review.json) supersedes earlier native-shell assumptions where stated, including the unavailable memory-command registration and compiled-out verbosity functions. [stub_query_review.json](stub_query_review.json) records exact instruction proofs for compiled-out handlers; their actual physical responses are in session 21.

The original firmware dump and emulator implementation were not changed by this capture work.
